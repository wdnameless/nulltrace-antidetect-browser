# Release setup

Что нужно сделать **в репозитории** (не в коде), чтобы выпускать релизы с работающими
автообновлениями. Всё, что можно было сделать кодом, уже сделано; здесь — только действия
владельца репозитория, требующие прав на GitHub.

## Что уже работает без вашего участия

- CI (`test` job) гоняет typecheck, unit-тесты, сборку и Rust-тесты на каждый push в `main` и на PR.
- `release` job собирает NSIS-установщик и портативный `.exe` и прикрепляет их к GitHub Release.
- Публичная половина minisign-ключа вшита в `src-tauri/tauri.conf.json`, а endpoint обновлений
  указывает на `https://github.com/wdnameless/nulltrace-antidetect-browser/releases/latest/download/latest.json`
  (совпадает с `git remote`).

## Настройка подписи с нуля

### Зачем она нужна

Tauri проверяет обновления по подписи. Сборка, выпущенная **без** подписи, не даст обновиться:
апдейтер отвергнет скачанный файл, потому что он не подтверждён приватным ключом.

Без секрета CI **намеренно** не публикует `latest.json` — вместо этого шаг пропускается, и
приложение честно сообщает «обновления не настроены». Это осознанный выбор: `latest.json` с
пустой подписью заставил бы апдейтер отвергать **все** релизы, при этом UI показывал бы проверку
как успешную — состояние хуже, чем отсутствие метаданных.

### Шаги

> **Текущее состояние (0.6.45)**: подпись работает — `latest.json` публикуется, обновления
> доставляются. Активный ключ записан в `resources/release-key-identity.json`, и тест падает,
> если `pubkey` в `tauri.conf.json` перестанет ему соответствовать.
>
> **Важно про ротацию ключа.** Ключ, которым подписаны релизы до 0.6.42, был заменён в 0.6.44
> (id `29F423F8EFA4DD7F` → `5BEF02FE54378830`), потому что его пароль был утерян. Замена была
> **ошибкой**: оказалось, что старая подпись работала, а гайд ниже описывал уже неактуальную
> проблему. Последствие: **сборки до 0.6.42 вшили СТАРЫЙ публичный ключ и не могут обновиться
> сами** — Tauri проверяет подпись в `download()` против ключа, вкомпилированного в запущенную
> сборку, поэтому такая сборка покажет «Update available» и упадёт на скачивании. Нужна одна
> ручная переустановка; начиная с 0.6.45 обновления идут нормально.
>
> Отсюда правило: **менять ключ подписи — только осознанным решением**, с записью в
> `release-key-identity.json` и примечанием в changelog. Молчаливая замена не ломает ни одну
> сборку и не роняет ни один тест, но оставляет без обновлений все установленные копии.

1. **Сгенерировать пару ключей** (один раз, локально). Требуется Tauri CLI:

   ```bash
   npx tauri signer generate -w "$env:USERPROFILE\.tauri\nulltrace.key"
   ```

   > **Проверьте, куда лёг файл.** В cmd.exe и PowerShell `~` не раскрывается: Tauri CLI
   > пишет ключ в буквальный подкаталог `~/.tauri` **внутри текущего каталога**. Если
   > команда выполнялась из репозитория, приватный ключ окажется в рабочем дереве — в одном
   > `git add -A` от попадания в историю. Используйте явный путь и убедитесь, что файл лежит
   > **вне** репозитория. `.gitignore` уже закрывает `~/`, `.tauri/` и файлы `*.key`/`*.key.pub`,
   > но полагаться только на него не стоит.

   Появится приватный ключ (записан в файл) и **публичный ключ** — он печатается в выводе.
   Пароль запрашивается интерактивно; чтобы задать его сразу, добавьте `-p <пароль>`, а чтобы
   обойтись **без пароля** — `-p ""` (тогда секрет с паролем не нужен вовсе).

   > Приватный ключ — это право выпускать обновления от имени вашего приложения. Он **не должен**
   > попадать в репозиторий, логи CI или переписку. Если он утёк — сгенерируйте новый и замените
   > публичную половину в `tauri.conf.json`.

2. **Проверить, что публичная половина совпадает.** Значение `pubkey` в
   `src-tauri/tauri.conf.json` (`plugins.updater.pubkey`) должно быть **тем самым** публичным ключом,
   который вы только что получили. Если вы генерируете пару впервые — замените значение на новое и
   закоммитьте; если ключ уже был — убедитесь, что он тот же, иначе обновления не пройдут проверку.

3. **Добавить два секрета репозитория**: GitHub → **Settings → Secrets and variables → Actions →
   New repository secret**.

   | Имя | Значение |
   |---|---|
   | `TAURI_SIGNING_PRIVATE_KEY` | содержимое приватного файла (`~/.tauri/nulltrace.key`) — вся строка целиком |
   | `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | пароль, заданный на шаге 1 |

   Имена должны совпадать точно: workflow читает именно `secrets.TAURI_SIGNING_PRIVATE_KEY` и
   `secrets.TAURI_SIGNING_PRIVATE_KEY_PASSWORD`.

4. **Выпустить релиз** — создать и запушить тег. Release job запускается **только** по тегу `v*`:

   ```bash
   # версия должна совпадать в package.json, src-tauri/tauri.conf.json и теге
   git tag v0.6.0
   git push origin v0.6.0
   ```

   После этого в GitHub Release появятся установщик, портативный `.exe`, `latest.json` и `.sig`.
   Приложение начнёт видеть обновления.

## Обновления не работают: диагностика и лечение

### Сначала проверьте это: коммиты и тег вообще дошли до GitHub?

Самая частая причина — не подпись и не манифест, а то, что релиза **не существует**: работа
сделана и закоммичена локально, но `git push` не выполнялся. Симптом ровно такой, как будто
обновления сломаны:

- В приложении футер показывает «Up to date» (или «Not checked»), хотя новая версия собрана.
- `releases/latest/download/latest.json` отвечает **старым** номером версии — той, что уже стоит.
- В списке тегов последний — предыдущая версия.

Проверка одной командой:

```bash
# Есть ли локальные коммиты, которых нет на GitHub? Если что-то выводится — релиза нет.
git log --oneline origin/main..HEAD

# Совпадает ли последний тег с версией в package.json?
git tag --sort=-creatordate | head -1
grep -m1 '"version"' package.json
```

**Только `git push origin <tag>` запускает публикацию.** Обычный `git push origin main` прогоняет
тесты, но release-job пропускается: он выполняется исключительно на теге `v*`. Версия
не появится в обновлениях, пока не будет тега.

Порядок выпуска:

```bash
git push origin main            # 1. код на GitHub, CI зелёный
git tag v0.6.14                 # 2. версия совпадает с package.json / tauri.conf.json / Cargo.toml
git push origin v0.6.14         # 3. это и публикует релиз
```

### Проверить опубликованную подпись, не дожидаясь чужой машины

После релиза полезно убедиться, что скачанный артефакт действительно подписан ключом, который
приложение доверяет. Это ровно та проверка, которую сделает апдейтер на другой машине:

```bash
node scripts/verify-release-signature.cjs <скачанный.exe> <скачанный.exe.sig> src-tauri/tauri.conf.json
```

Скрипт читает публичный ключ из `tauri.conf.json`, разбирает minisign-подпись и проверяет её
через встроенный Ed25519 в Node — независимо от `tauri signer`, которым релиз подписывался.
Важно: подпись формата `ED` покрывает BLAKE2b-512 хеш файла, а не сырые байты.

### Как выглядит проблема с подписью

- Релиз публикуется, но `latest.json` в нём **нет**: `releases/latest/download/latest.json` → **404**.
- В приложении футер показывает **«Updates not configured»**.
- В логе релиза шаг **Build updater manifest** падает с:
  `incorrect updater private key password: Wrong password for that key`,
  после чего срабатывает предупреждение **Updater metadata not produced**.

### Почему это происходит

Tauri проверяет обновление по подписи. Схема из трёх частей, и все три должны указывать на **одну**
пару ключей:

| Часть | Где живёт | Роль |
|---|---|---|
| Приватный ключ | секрет `TAURI_SIGNING_PRIVATE_KEY` | подписывает артефакт в CI |
| Пароль ключа | секрет `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | расшифровывает приватный ключ |
| Публичный ключ | `plugins.updater.pubkey` в `src-tauri/tauri.conf.json` | проверяет подпись у пользователя |

Ошибка «Wrong password» означает, что **пароль не соответствует приватному ключу**. Сам ключ при
этом валиден: битый ключ дал бы ошибку декодирования, а не «Wrong password».

Доказано на этой машине:

- с локальным ключом и **пустым** паролем → `Wrong password for that key`;
- в CI с секретом-паролем → **та же** ошибка.

Типичные причины: пароль введён с опечаткой; при вставке добавился перевод строки; ключ пересоздавали,
а пароль оставили от старого.

### Как убедиться, что публичный ключ парный

Проверка одной командой — она ответит `SIGNATURE VALID` только для своей пары:

```bash
cargo run --quiet --manifest-path src-tauri/Cargo.toml --example verify_minisign -- \
  "$(cat ~/.tauri/nulltrace.key.pub)" \
  <артефакт>.sig <артефакт>
```

Несовпадение даёт `SIGNATURE INVALID: The signature was created with a different key than the one
provided`. Это самая частая ошибка при ротации: подпись новым ключом + старый `pubkey` в конфиге.

### Решение A — ключ без пароля (рекомендуется)

Пароль не обязателен. Ключ, созданный с пустым паролем, подписывает **без** него — и целый класс
ошибок «Wrong password» исчезает. Проверено: такой ключ подписывает, а подпись проходит верификацию
штатным `verify_minisign` (`SIGNATURE VALID`).

> Это осознанный компромисс по безопасности: приватный ключ лежит только в секретах GitHub и
> доступен тому, у кого есть права на репозиторий. Пароль добавляет защиту лишь на случай утечки
> самого файла ключа. Если для вас это важно — используйте решение B.

```bash
# 1. Новая пара БЕЗ пароля. Явный путь: `~` не раскрывается в cmd/PowerShell,
#    и Tauri создаст буквальный каталог `~` внутри текущей папки.
npx tauri signer generate -w "$env:USERPROFILE\.tauri\nulltrace.key" -p ""

# 2. Публичную половину — в конфиг (иначе приложение отвергнет подпись).
#    Скопируйте содержимое nulltrace.key.pub целиком в plugins.updater.pubkey.
```

Секреты (значение — точная строка, **без** завершающего перевода строки):

```bash
# Приватный ключ: содержимое файла одной строкой.
tr -d '\r\n' < "$USERPROFILE/.tauri/nulltrace.key" | gh secret set TAURI_SIGNING_PRIVATE_KEY

# Пустой пароль. --body не добавляет перевод строки (в отличие от пайпа из echo).
gh secret set TAURI_SIGNING_PRIVATE_KEY_PASSWORD --body ''
```

Затем: закоммитить новый `pubkey`, **поднять версию** (тег уже израсходован — см. ниже) и выпустить тег.

### Решение B — восстановить пароль

Секреты GitHub **нельзя прочитать обратно**, поэтому подобрать значение невозможно — только задать
заново:

```bash
# Ошибка в пароле с переводом строки — самая частая. --body пишет ровно то, что передали.
gh secret set TAURI_SIGNING_PRIVATE_KEY_PASSWORD --body 'ваш-пароль'
```

Проверить, что пара «ключ + пароль» верна, **до** выпуска тега — локально, той же командой, что
выполняет CI:

```bash
TAURI_SIGNING_PRIVATE_KEY="$(tr -d '\r\n' < "$USERPROFILE/.tauri/nulltrace.key")" \
TAURI_SIGNING_PRIVATE_KEY_PASSWORD='ваш-пароль' \
node scripts/build-updater-manifest.mjs \
  --version 0.6.0 \
  --url https://example.com/x.exe \
  --artefact src-tauri/target/release/bundle/nsis/NullTrace_0.6.0_x64-setup.exe \
  --out dist-release
```

Успех — файлы `latest.json` и `.sig` в `dist-release/`. Ошибка — тот же текст, что увидит CI,
но без сожжённого тега.

### Проверка результата

1. Локально — команда выше создаёт `latest.json` и `.sig`.
2. В GitHub Release рядом с `.exe` лежат `latest.json` и `NullTrace_<версия>_x64-setup.exe.sig`.
3. `https://github.com/<owner>/<repo>/releases/latest/download/latest.json` отдаёт **200**, не 404.
4. В приложении футер показывает «Up to date» или «Update available» — не «Updates not configured».
5. Нажать версию в футере **один раз**: футер должен сам пройти
   `Checking…` → `Update available` → `Downloading… N%` → `Restart to update` → `Installing…`
   и приложение — перезапуститься уже новой версией. Остановка на `Update available` означает,
   что клик снова ведёт только проверку.

   Приложение при этом закрывается — это ожидаемо и обязательно: portable-сборка не может
   заменить свой лаунчер, пока работает. Обновление завершает отдельный помощник, который ждёт
   выхода процесса, подменяет файл и запускает новую версию.

6. Если обновление не поднялось — рядом с лаунчером появляется `<имя>.update-failed` с причиной,
   а сам лаунчер и файл `.new` остаются на месте для повторной попытки. Молчаливого «ничего не
   произошло» больше нет: неудачная подмена не запускает старую версию.

### Не сжигайте теги впустую

Тег — это идентичность релиза, и повторно использовать его нельзя: прогон уже привязан к нему.
Тег, выпущенный до исправления подписи, даёт опубликованные установщики **без** `latest.json`.
Поэтому порядок такой: **сначала** проверка подписи локально, **потом** тег.

### Полезно знать

- Шаг подписи помечен `continue-on-error`: если подпись не удалась, установщики всё равно
  публикуются, а в логе появляется предупреждение с причиной. Релиз не теряется целиком.
- `latest.json` **нельзя** публиковать вручную из неподписанной сборки: апдейтер отвергнет
  обновление у всех, а интерфейс будет показывать проверку как успешную.
- Endpoint разрешается в **последний** релиз репозитория. Меняя репозиторий, переносите туда артефакты.

## Чего делать НЕ нужно

- **Не коммитить приватный ключ** ни в каком виде (в т.ч. в `.env`, скриншотах, issue).
- **Не публиковать `latest.json` вручную** из неподписанной сборки — см. объяснение выше.
- **Не менять `endpoints`** на другой репозиторий без переноса туда артефактов: endpoint
  разрешается в `releases/latest/download/latest.json`, то есть в **последний** релиз репозитория.

## Обновление версии

Версия фигурирует в трёх местах и должна совпадать с тегом:

| Файл | Поле |
|---|---|
| `package.json` | `version` |
| `src-tauri/tauri.conf.json` | `version` |
| `src-tauri/Cargo.toml` | `version` |
| git-тег | `v<version>` |

`latest.json` формируется скриптом `scripts/build-updater-manifest.mjs`, который берёт версию из
тега (`--version "${{ github.ref_name }}".Replace('v','')`).
