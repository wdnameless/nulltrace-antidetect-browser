# NullTrace

**Zero footprint, infinite scale.** _Leave nothing behind._

Персональный антидетект-браузер — функциональный клон **AdsPower**, заточенный под связку с собственными автоматизациями через Local API.

> Статус: **MVP собран (Фазы 0–5).** Устанавливаемый Windows-инсталлятор готов и верифицирован: профили, фингерпринты (kernel-level stealth, `webdriver=false`), прокси-менеджер (HTTP/HTTPS/SOCKS5/SSH + авторизация через CDP + авто-timezone), смена девайса, AdsPower-совместимый Local API. См. `docs/ROADMAP.md`, `docs/ENVIRONMENT.md`.

## Что это

Десктоп-приложение (Windows), которое:

- создаёт **изолированные браузерные профили** (отдельные cookies, fingerprint, прокси на профиль);
- управляет **безлимитными прокси** (HTTP/HTTPS/SOCKS5/SSH);
- генерирует и привязывает **фингерпринты** (kernel-level спуфинг через патченый Chromium);
- поддерживает **смену девайса** (пресеты Win/macOS/iOS/Android);
- предоставляет **AdsPower-совместимый Local REST API** — главная фича: ваши скрипты (Puppeteer / Playwright / Selenium / Python) запускают профиль и получают CDP-эндпоинт для полного управления.

## Ключевой принцип автоматизации

API не управляет страницами сам. Он **запускает изолированный браузер** и отдаёт CDP WebSocket-эндпоинт. Дальше ваша автоматизация рулит браузером напрямую через `connectOverCDP` / `debuggerAddress`. Это 1-в-1 модель AdsPower, поэтому существующие AdsPower-скрипты и MCP работают без переделки.

## Быстрый старт

```bash
npm install
npm run dev                # Tauri-оболочка + Vite (UI + Local API)

# или только бэкенд без UI:
npm run service            # Local API на http://localhost:50325 (API-ключ печатается в консоль)
```

Браузерное ядро (~425 МБ патченого Chromium) **не входит в сборку** — иначе артефакт вырос бы
вчетверо. Оно ставится один раз из интерфейса: **Settings → Browser Kernel → «Скачать и
установить ядро»**, с прогрессом загрузки и проверкой SHA-256. Пока ядра нет, профили не
запускаются, и приложение сообщает об этом прямо, а не падает молча.

Для оффлайн-установки ядро можно положить рядом вручную: `npm run ensure-kernel` скачивает его
в `data/chromium/fingerprint-chromium`.

## Портативные сборки / Portable Distribution

NullTrace поддерживает запуск без инсталлятора на всех трех поддерживаемых платформах:

- **Windows**: единый портативный исполняемый файл `.exe` (`NullTrace-<version>-portable-win-x64.exe`). Запускается без прав администратора, хранит секреты через Windows DPAPI (`CurrentUser`, `src-tauri/src/secrets.rs`).
- **Linux**: портативный пакет `.AppImage` (`NullTrace-<version>-portable-linux-x64.AppImage`).
- **macOS**: образ диска `.dmg` (`NullTrace-<version>-portable-mac-arm64.dmg`) под архитектуру Apple Silicon (arm64).

### Ограничения macOS / macOS Limitations

1. **Не является single-file**: на macOS дистрибутив поставляется в виде `.dmg`, содержащего `.app`-бандл приложения. В силу архитектуры macOS и правил формирования Application Bundle, поставка в виде единого бинарного файла невозможна.
2. **Подпись ad-hoc, без Developer ID и нотаризации**: у проекта нет платного Apple Developer account, поэтому сборка не подписана сертификатом разработчика. Однако на Apple Silicon любой arm64-код обязан иметь подпись — иначе его откажется загружать ядро системы, независимо от Gatekeeper. Поэтому сборка автоматически подписывается **ad-hoc** (`codesign -s -`, бесплатно, без сертификата): это удовлетворяет загрузчик, но не Gatekeeper.
3. **Карантин Gatekeeper**: при первом запуске macOS заблокирует запуск, потому что подпись ad-hoc не выдаёт Developer ID. Чтобы запустить приложение, необходимо один раз снять атрибут карантина в терминале:
   ```bash
   xattr -dr com.apple.quarantine /Applications/NullTrace.app
   ```
   (или указать путь к скачанному `.app` / смонтированному образу). Developer ID + нотаризация убрали бы этот шаг, но не требуются для запуска.

## Сборка десктопного дистрибутива (Tauri v2)

Основным десктопным билдом является оболочка Tauri v2 (`src-tauri/`), запускающая локальный автономный сервис Node.js в режиме sidecar и отображающая интерфейс через системный WebView (WebView2 на Windows):

```bash
npm run vendor:node          # Подготовка runtime Node.js в src-tauri/binaries/
npm run tauri:build          # Сборка нативного десктопного приложения Tauri
```

Electron удалён из проекта: каталога `electron/`, зависимостей и скриптов `dist:*` больше нет.
Десктопная оболочка Tauri v2 — единственный нативный билд.

### Первый запуск: где хранятся данные

При первом запуске приложение спрашивает, **куда сохранять профили, ядро браузера, расширения и
резервные копии**. Это десятки гигабайт, поэтому путь выбирается один раз, до создания данных:
у установленной сборки по умолчанию это профиль пользователя (`%APPDATA%\antidetect-browser\data`
на Windows), который нередко лежит на небольшом системном диске.

- Экран предлагает конкретный путь и позволяет выбрать другой (**Обзор…** или ручной ввод).
- Папка **проверяется на запись до сохранения**: непригодный путь (файл вместо папки, каталог
  только для чтения) отклоняется сразу с указанием причины.
- Выбор применяется **перезапуском** — `DATA_DIR` вычисляется один раз при старте сервиса, и
  переносить живую базу данных «на ходу» было бы хуже перезапуска. Приложение перезапускается само.
- Изменить расположение позже можно в **Settings → Data directory** (там же перенос существующих
  данных через `POST /api/v1/data/migrate`).

Запрос **не появляется**, когда путь задан извне: если выставлен `ANTIDETECT_DATA_DIR` (CI, тесты,
управляемое развёртывание), включён server mode, либо ответ уже сохранён ранее — повторно спрашивать
оператора, у которого уже есть десятки гигабайт профилей, было бы ошибкой.

Примеры подключения автоматизаций — в [`examples/`](examples/). Тесты — [`scripts/smoke.ts`](scripts/smoke.ts), [`scripts/smoke-automation.ts`](scripts/smoke-automation.ts), [`scripts/verify-stealth.ts`](scripts/verify-stealth.ts) (Фаза 2: `webdriver=false` + уникальность фингерпринтов), [`scripts/smoke-proxy.ts`](scripts/smoke-proxy.ts) (Фаза 3), [`scripts/verify-device.ts`](scripts/verify-device.ts) (Фаза 4).


## Десктоп-оболочка Tauri

Десктопное приложение собрано на базе [Tauri v2](https://tauri.app) (`src-tauri/`) и заменяет Electron в качестве основного десктопного билда.

### Честное разграничение: что требует установки, а что нет

1. **Веб-интерфейс (`npm run service`)** — это то, что **действительно не требует установки** и работает с нулевым следом: запускается локальный HTTP-сервис (`API_PORT=50325`), открывается в любом стандартном браузере (Chrome, Edge, Firefox, Safari), не устанавливает десктопных приложений.
2. **Tauri-оболочка (`src-tauri`)** — это **устанавливаемое / исполняемое нативное десктопное приложение**. Мы честно заявляем: оболочка является нативным бинарником для конкретной ОС, а не веб-страницей. Она запускает локальный Node.js-сервис в режиме sidecar и отображает интерфейс через системный WebView (WebView2 на Windows, WebKitGTK на Linux, WKWebView на macOS).

### Ограничения платформ, верификация и подпись (macOS Gatekeeper / Quarantine)

- **Windows — основная собранная и верифицированная платформа**: под Windows реализован и протестирован полный цикл запуска, WebView2, Rust DPAPI (`src-tauri/src/secrets.rs`), системный трей, updater и управление жизненным циклом бекенда.
- **macOS (Apple Silicon) — собранная и проверенная**: артефакт `NullTrace-<версия>-macos-arm64.zip` публикуется CI на раннере `macos-14`; ядро браузера работает там **нативно под arm64** (`lipo -archs: arm64`), `navigator.webdriver === false` под CDP, флаги `--fingerprint` проверены измерением — подробности в [`docs/KERNEL.md`](docs/KERNEL.md). Известные ограничения перечислены ниже.
- **Linux — только конфигурация (configuration only)**: конфигурационные файлы подготовлены (`src-tauri/tauri.conf.json`), но **готовые артефакты не публикуются** и на этой платформе не верифицировались.
- **Защита экрана и Win32-ограничения**: защита от захвата экрана и скриншотов (`set_content_protected`) реализована кроссплатформенно. Однако автоблокировка по таймауту бездействия (measured-idle) и блокировка окна при блокировке сессии ОС (session-lock) в этой версии реализованы **только под Windows** (через Win32 API `GetLastInputInfo`, `WM_POWERBROADCAST` и `WTSRegisterSessionNotification`). На macOS и Linux эти функции пока не поддерживаются.
- **Ядро Chromium не бандлится в дистрибутив**: браузерное ядро (fingerprint-chromium, ~425 МБ) не запекается в инсталлятор, иначе артефакт вырос бы с 48 МБ примерно до 470 МБ. Оно ставится один раз из интерфейса (**Settings → Browser Kernel**), с прогрессом и проверкой SHA-256; для оффлайн-развёртывания предусмотрен `npm run ensure-kernel`. Пока ядра нет, запуск профиля невозможен и приложение сообщает об этом явно.
- **Обновления (Windows)**: проверка и установка идут через подписанный манифест `latest.json`. Артефакт подписывается minisign-ключом; **публичная** половина ключа вшита в `tauri.conf.json`, **приватная** хранится только в CI-секрете и в репозиторий не попадает. Если ключ не настроен, приложение честно сообщает, что автообновления не сконфигурированы для этой сборки, — вместо красной ошибки на пустом месте. Обновляется **одним нажатием на версию в футере**: `проверка → скачивание → установка → перезапуск`, с прогрессом на месте. Работает и для установленной сборки, и для single-file portable: portable-сборка не может подменить свой лаунчер, пока работает, поэтому приложение закрывается, отдельный помощник дожидается выхода процесса, заменяет файл и запускает новую версию уже без ручных действий. Если подмена не удалась, рядом с лаунчером появляется `<имя>.update-failed`, а старая версия не перезапускается — молчаливого «ничего не произошло» нет. **Что нужно настроить в репозитории, чтобы это заработало — в [`docs/RELEASE.md`](docs/RELEASE.md).**
- **MCP-привилегии**: MCP-сервер запускается из приложения и по умолчанию работает на уровне `standard` — 35 инструментов чтения/записи доступны, 12 деструктивных (удаление, восстановление, импорт/экспорт) отклоняются. Включить их можно в **Settings → Security → MCP privileges → Admin**; изменение применяется при следующем старте MCP.
- **macOS (arm64 Apple Silicon)**: на Apple Silicon любой arm64-код обязан иметь подпись — иначе ядро откажется его загружать, независимо от Gatekeeper. Сборка **не подписана** платным сертификатом разработчика (у проекта нет Apple Developer account), используется только ad-hoc подпись (`bundle.macos.signingIdentity = "-"`).
- **Карантин Gatekeeper**: подпись ad-hoc не выдаёт Developer ID, поэтому при первом запуске на macOS система заблокирует запуск. Снять карантин нужно один раз:
  ```bash
  xattr -dr com.apple.quarantine /Applications/NullTrace.app
  ```

### macOS: форма portable и что там не работает

**Форма — папка, а не один файл.** Это ограничение платформы, а не наше решение: приложение на
macOS — это `.app`, то есть каталог, и распаковать его при запуске из одного файла, как делает
Windows-лаунчер, нельзя. Артефакт `NullTrace-<версия>-macos-arm64.zip` содержит папку
`NullTrace-<версия>-macos-arm64` с `NullTrace.app`, пустой помеченной папкой `data/` и
`README-FIRST.txt`. Распакуйте папку куда угодно — данные (профили, ядро, расширения, база) лежат
**рядом** с приложением, поэтому перенос папки переносит всё. Внутрь `.app` не пишется ничего: это
сломало бы подпись, и macOS отказался бы запускать изменённый бандл (проверяется
`codesign --verify --deep --strict` после прогона).

**Запускать надо из этой папки.** Если перетащить `.app` в `/Applications`, портативный режим
включаться **не будет**, и это сделано намеренно: обычный пользователь не может писать в
`/Applications`, поэтому приложение откатывается на штатное для macOS место
(`~/Library/Application Support/antidetect-browser`) и работает как обычная установка. Иначе оно
упало бы на первой же записи настроек с невнятной ошибкой доступа. Проверка — попыткой создать
файл в папке, а не флагом «read-only»: `/Applications` не «только для чтения» по режиму, но писать
туда нельзя.

**Чего на macOS нет:**

- Автоблокировка по бездействию (measured-idle) и блокировка при блокировке сессии ОС
  (session-lock) — они реализованы только под Windows через Win32 API.
- Автообновление. Механизм подмены лаунчера (`build_windows_swap_command`) — Windows-специфичный;
  для macOS он не реализован, поэтому метаданные обновления для неё **не публикуются**: приложение
  честно сообщает, что автообновления не сконфигурированы, вместо обещания, которое не выполнит.
- **Интел-маки.** Артефакт только под arm64, и запустить на Intel его нельзя — см. ниже, это
  ограничение самого ядра.

**Apple Silicon обязателен, и это ограничение ядра, а не наше.** Образ ядра, который публикует
upstream, содержит **только arm64**: на Intel-маке (контрольный прогон на `macos-15-intel`)
запуск падает с `spawn Unknown system error -86` — это `EBADARCH`, «неверная архитектура». Rosetta
работает в обратную сторону (arm64-код на Intel не выполняется), поэтому запустить это ядро на
Intel-маке невозможно в принципе. Альтернативы: либо upstream выпустит x86_64-образ, либо Intel не
поддерживается.

**Что осталось непроверенным:** запуск `.app` на живом Маке (сборка бандла и подпись проверяются в
CI, но именно клик по приложению с профилями — воспроизводит оператор) и поведение при переносе
`.app` на другой Мак: macOS кэширует путь бандла, и ad-hoc подпись может потребовать повторного
подписания. Это записано как риск в `openspec/changes/nulltrace-macos-arm64`.
